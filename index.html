JamEMR: product overview and engineering evaluation

An AI-native electronic medical record. Structured clinical facts are the source of truth. AI drafts and proposes; clinicians decide and sign. This document explains what the product does, how it is built, how far each capability has been verified, and where outside engineering and infrastructure work would help most.

Verification limits, up front

Part I · Product overview

1What JamEMR is

JamEMR is an electronic medical record for outpatient specialty practice, built from scratch to work with AI. Today it is aimed mainly at neurology. It covers the front office (registration, scheduling, check-in, kiosk), clinical documentation (ambient visit capture, dictation, notes), the chart itself (problems, medications, allergies, results, vitals), and a broad set of supporting modules: orders, billing aids, referrals, a patient portal, research tooling and EHR interoperability.

Two design principles shape everything else:

Facts, not notes, are the record

Every clinical datum is a structured, versioned clinical fact: a diagnosis, a medication and dose, an allergy, a vital, a result. Each fact has provenance (who or what produced it, from which source, with what evidence). Notes are rendered from facts. A note is a view of the chart, not the chart.

AI drafts; humans attest

Anything produced by an AI model or device enters the chart as pending attestation. Only a human clinician can approve it, and the attestation is bound to the exact text they reviewed. A governance layer refuses AI-initiated prescribing, order signing, diagnosis finalisation, claim submission and note attestation.

Problems it addresses

  • Documentation burden. The visit is recorded with consent and transcribed on local hardware. Medications, seizure frequency, allergies and other facts are extracted, and a draft note is assembled for the clinician to review and sign.
  • Fragmented prior records. "Import Records" takes PDFs, images, ZIPs, C-CDA and FHIR documents, plus pulls from cloud document stores. It extracts facts with verbatim evidence and routes uncertain items to a review queue instead of the chart.
  • Unsafe AI output. Quotes are verified against the source text, negations are grounded, unknown drug names are dropped, and medication changes are reconciled against the chart. Placeholders and "not ready" markers block signing.
  • Data residency for PHI. In PHI mode, every model call must go to an approved local model on the host itself. The service refuses to start otherwise.

3How the modules fit together

All modules read and write one store of clinical facts, which sits behind a single attestation gate. Capture modules feed facts in; review modules turn pending facts into attested ones; output modules render, code, transmit or analyse attested facts.

Bottom line for an evaluating team

The core of JamEMR at a07bc2a (the fact store, provenance, human-only attestation, access control, PHI egress guards and the deterministic clinical pipeline) is substantial, well structured and heavily tested at the unit and API level. The parts that make it a production clinical system are mostly unfinished or unverified: clinical-quality evaluation of real models and real audio, live vendor integrations (e-prescribing, clearinghouse, fax, the EHR of record), high availability, off-host backup, observability, CI on Postgres, and the legal and compliance programme. The pilot release gates recorded in the repository (19 Oct 2026) were not met, and the repository records no go-live decision since then. JamEMR should be evaluated as a pre-production platform.

7Step by step

7.1Patient creation, prior-record import, duplicates· Front desk · Physician1 · Verified
What the user does
The front desk registers the patient (front-desk.html). If a possible duplicate is found, a dialog asks them to confirm and give a reason code and free-text reason before the chart is created. Prior records are brought in through Import Records in the physician workspace: upload a file, ZIP or image, choose a local path, or pull from a connected cloud document store.
What the system does
POST /api/patients (api/clinical.py, permission patient:register) → patient_service.find_duplicates_checked, which matches on MRN, or on family name + DOB + compatible given name. A match returns 409 potential_duplicate; an override is audited in the same transaction. Writes patient (encrypted demographics), provenance_entry, a PATIENT_REGISTERED event, and patient_care_team (creator = owner). Import uses /api/import-batches/* in this order: extract → match/create-patient → commit. The alternative /api/chart-import/.../auto-import writes deterministic facts at confidence 0.9 as pending attestation and sends ambiguous items to a review queue.
AI involvement
Import: deterministic extractors always run. LLM augmentation of narrative segments is off by default (JAMEMR_IMPORT_LLM_EXTRACTION). Every LLM quote must match the source verbatim.
Safeguards
Duplicate detection with an audited override. Import conflicts are never auto-resolved, and a high-severity conflict blocks commit. Local import paths are confined to allow-listed roots.
Result
A patient chart with care-team ownership. Imported facts are either attested by the reviewing clinician at commit, or pending attestation (auto-import path).
Test evidence
test_patient_dedup*.py (policy, override, concurrency), test_patient_merge.py, about 30 test_import_* files, test_prechart_commit.py, test_phase4_lifecycle.py
Verification on a07bc2a
Run and passed: G04 duplicate detection (34), G05 merge/lifecycle (18), G13 Import Records (223 passed, 2 skipped needing Node).
Limits & open issues
Import's create-patient path refuses only an exact-MRN duplicate (weaker than registration). Import commit silently swallows attestation exceptions (import_service.py ~L3405). Merge marks merged_into and keeps the row. Hard PHI deletion is a separate dry-run → confirm → verify → tombstone workflow, and there is no simple soft-delete. OCR depends on an external local service.
7.2Scheduling, check-in and encounter setup· Front desk · MA1 · Verified
What the user does
The front desk books the appointment and confirms identity at check-in (name + DOB), or the patient checks in at the kiosk with last name, DOB and a printed code. The MA picks the patient on the Rooming page, opens the encounter, records vitals and reconciles medications and allergies.
What the system does
/api/scheduling/appointments, /confirm-identity, /check-in, /appointments/{id}/encounter, /status (api/scheduling.py). encounter_service.open_for_appointment is idempotent (one encounter per appointment) and refuses cancelled, no-show or completed appointments and unconfirmed identity. POST /api/facts records vitals. Tables: appointment, encounter (status in_progress, capture_state=idle), clinical_fact, access_audit.
AI involvement
None.
Safeguards
The identity-confirmation guard is on in production-like environments. An MA holds only fact:write:rooming, and any judgement-type fact an MA writes is forced to pending physician attestation. Vitals are human-authored and need no attestation.
Result
An open encounter tied to the appointment, with vitals in the chart.
Test evidence
test_scheduling.py, test_recurring_scheduling.py, test_day_schedule.py, test_kiosk.py, test_pilot_patient_identity.py, test_encounter_rollup.py
Verification on a07bc2a
Run and passed: G06 scheduling/check-in/kiosk (32), G07 encounter and MA rooming (48).
Limits & open issues
Reminder delivery needs an SMS or email provider. The default comms provider is a fake. Telehealth exists only as a scheduling modality, with no video.
7.3Ambient recording and dictation· Physician2 · Not verified
What the user does
In the chart, the physician records the patient's consent, then presses Start ambient visit. The browser captures audio (getUserMedia + MediaRecorder, webm/opus). Alternatively, the standalone Dictation page records, uploads or accepts pasted text, which is later attached to a patient.
What the system does
POST /api/encounters/{id}/recording-consent → recording_consent. The default path uploads the whole recording at the end: POST /api/encounters/{id}/transcribe (base64 in a JSON body). While recording, 60-second chunks go to /transcribe-partial, which produces a preview only and writes nothing to the chart. A WebSocket /api/encounters/{id}/stream exists but is behind JAMEMR_STREAMING_ENABLED (off). encounter.capture_state moves idle → listening → recorded.
AI involvement
None at capture.
Safeguards
Consent is required by default (JAMEMR_REQUIRE_RECORDING_CONSENT). In PHI mode, audio is refused (503) unless three operator attestations are set: audio ingest enabled, storage verified, lifecycle verified. All three default to false. Dictations expire after 72 h.
Result
A stored audio blob linked to the encounter, and a consent record.
Test evidence
test_recording_consent.py, test_wp10_dictation.py, test_m4_streaming.py, test_stream_audio_purge.py, test_audio_lifecycle.py
Verification on a07bc2a
Partly run: G08 recording consent (9 passed). Audio capture and upload tests exist but were not run in this review. No test uses real audio.
Limits & open issues
Batch only. The "streaming" path re-transcribes the accumulated buffer and is not true streaming ASR. Capture was not exercised end to end with real audio for this document.
7.4Transcription· System (local speech service)2 · Not verified
What the user does
Nothing, beyond waiting about 1–3 minutes. Afterwards the physician can relabel speakers or correct transcript segments.
What the system does
transcription_service.transcribe_encounter is idempotent on the audio's SHA-256. The engine is chosen by JAMEMR_DIARIZATION_BACKEND: dgx_audio (default; an external local service on loopback, using upload → job → poll for up to 600 s), nemo (in-process Parakeet-TDT 1.1B + Sortformer diariser, optional extra), or fake (CI). Then optional re-healing of garbled passages, deterministic drug-name correction, and encounter_transcript (segments, raw segments, corrections) with DEVICE provenance. Finally, the speech service's copy of the audio is purged.
AI involvement
Speech-to-text model (Whisper-class in the external service, or NeMo). There is no cloud fallback.
Safeguards
On failure the audio is kept and the API returns 503, with a manual /transcribe/retry. Silence returns 422. The PHI egress guard applies.
Result
A transcript with corrections recorded. capture_state=recorded.
Test evidence
test_audio_transcription.py, test_diarization_backends.py, test_transcript_review.py, test_transcribe_multiprocess_postgres.py (Postgres lane)
Verification on a07bc2a
Not run in this review. Tests exist and use a fake transcriber. Real ASR has never been exercised by an automated test.
Limits & open issues
The ASR service is not in this repository, and its API contract is noted in code as "to be confirmed". JAMEMR_AMBIENT_SINGLE_SPEAKER=1 by default, so everything is attributed to the physician and diarisation is effectively off. CI tests use a fake transcriber. Real-audio accuracy has not been measured.
7.5Extraction of clinical facts· System2 · Not verified
What the user does
Nothing directly. Extracted facts appear as pending cards in the chart.
What the system does
POST /api/transcripts/{id}/extract → extract_from_transcript. Deterministic neurology extractors (migraine, seizure) run first. Then llm_extraction_service.extract_candidate_facts runs over 4,000-character windows with 300 overlap, prompt extract-v2.1. Results are filtered: unknown drug names are dropped, duplicates of deterministic facts are removed, and medications are reconciled against the chart. A conflict sets ready_for_attestation=False and is never auto-applied. The whole run is atomic: a new fact set replaces the previous one, and a failure rolls back.
AI involvement
Local LLM (router first pass medgemma-27b, or JAMEMR_AMBIENT_MODEL). Untrusted text is stripped of injected instructions first.
Safeguards
Verbatim-quote verification. Hedged "no known allergies" claims are re-checked. Speech about someone other than the patient becomes family history. A code is kept only if it validates in strict terminology mode. Every fact is author_type=ai_agent and therefore pending attestation.
Result
clinical_fact rows (pending), ai_event rows, provenance.
Test evidence
test_llm_extraction_governance.py, test_ambient_neuro_extraction.py, test_migraine_ambient_extraction.py, test_m4_windowed_extraction.py, test_nkda_faithful_extraction.py, test_extract_llm_failure.py
Verification on a07bc2a
Partly run: G09 deterministic extraction (45 passed). LLM extraction tests exist (stubbed LLM) and were not run here.
Limits & open issues
The deterministic extractors are neurology-only. LLM facts' provenance records JAMEMR_LLM_MODEL although the call used the ambient model (mislabel). Confidence is a float (LLM default 0.6) rather than a calibrated score. Extraction quality on the production model is not measured; one recorded A/B gives F0.5 ≈ 0.44.
7.6Draft note generation· System2 · Not verified
What the user does
The physician opens the draft note, or generates one of the note types (progress/SOAP, H&P, consult, procedure, discharge, A–Y neurology note, PI consult).
What the system does
Ambient: neuro_note_service.render_neuro_note produces a note_artifact (neuro progress note, DRAFT, AI author) in a deterministic house format with safety-alert and NOT-READY markers. Generic: POST /api/notes/render → render_note_from_facts (deterministic, plus admin-published templates). A–Y: POST /api/patients/{id}/clinical-note/generate, where about 20 sections are deterministic and the LLM writes only HPI and Assessment & Plan.
AI involvement
Only the A–Y note's HPI and A&P (jamemr-medical), within a total budget of 55 s. LLM polish of the ambient note is hard-disabled (POLISH_ENABLED=False).
Safeguards
LLM text is grounded against the source and negations are checked. On timeout, an "AI unavailable" placeholder is inserted, and it blocks signing.
Result
A draft note_artifact listing the fact ids it was rendered from. capture_state=ready_for_review.
Test evidence
test_clinical_note.py, test_kb_and_neuro_note.py, test_pilot_neuro_note_llm_deadline.py, test_pi_consult_note.py
Verification on a07bc2a
Partly run: G10 deterministic note rendering (16 passed). A–Y LLM-section tests exist and were not run here.
Limits & open issues
The ambient note is always a neurology note, whatever the specialty. The A–Y generator embeds a hard-coded clinician signature constant. The PI consult job state lives in process memory, so it is lost on restart and does not work with multiple workers. Specialty JSON profiles exist but no note-plugin system is wired into the ambient path. Generating negatives and a "normal exam" on sparse charts is a recorded open clinical decision.
7.7Clinician review· Physician1 · Verified
What the user does
The physician reviews pending fact cards (approve, reject, or fix first), edits the note text, optionally asks for an AI Refine, accepts or dismisses suggested additions, confirms medication sections, and runs the pre-sign check.
What the system does
Fact cards are handled by /api/attest (single or batch; each fact still gets its own attestation) and /api/facts/{id}/retract. Contradictions come from GET /api/attest/contradictions (advisory). Note edits go through PUT /api/notes/{id}/text, which needs a version token (base_text_sha256 or If-Match); a stale token returns 409 edit_conflict with the user's text preserved. Refine is POST /api/notes/{id}/refine and produces a new draft. Medication sections use /notes/{id}/medication-sections/preview|apply. The pre-sign check is GET /notes/{id}/precheck.
AI involvement
Refine (LLM). A claim guard rejects numbers that do not appear in the source.
Safeguards
Precheck blockers: placeholders, NOT-READY markers, empty notes, AI output-check failures, a stale medication source, record-review checks. Warnings: contradictions, unclear allergy status, extraction gaps, an AI draft never edited by a human. Precheck returns text_sha256, which signing must echo back.
Result
A reviewed draft and a set of approved or rejected facts.
Test evidence
test_contradictions.py, test_note_workspace_shell.py, test_wp8_note_reflow.py, test_pilot_g6_refine_unverified_block.py, test_pilot_med_update_sections.py, plus browser-lane note tests
Verification on a07bc2a
Run and passed: G11 note editing, refine guard, precheck, addenda (56); G20 contradictions, medication sections (103 in group).
Limits & open issues
The medication-confirmation redesign is on a separate unmerged branch. Contradiction checks are advisory only.
7.8Attestation and signing· Physician only1 · Verified
What the user does
The physician presses Sign (for a note) or Approve (for a fact).
What the system does
POST /api/attest (api/governance.py) → attestation_service.attest. The attester must be the authenticated HUMAN user; signing on behalf of someone else returns 403, and a wrong patient (X-Active-Patient) returns 409. A note sign requires expected_text_sha256. Lock order: patient medication advisory lock, then the note row FOR UPDATE, with the hash re-checked before and after. Fact approval is a conditional UPDATE that succeeds only if the fact is still current. Writes attestation, provenance attested, and an event.
AI involvement
None. Governance refuses AI attestation.
Safeguards
Bound to the reviewed text. Re-checks blockers. Retracted is terminal. Flipping a decision requires an amendment.
Result
An attested note or fact. capture_state=signed.
Test evidence
test_attestation_state_machine.py, test_attest_locked_text_check.py, test_attest_race_postgres.py (Postgres lane), test_pilot_stale_text_identity.py, test_signed_note_presentation.py
Verification on a07bc2a
Run and passed: G03 attestation (21 passed, 1 skipped needing Node); G20 sign-identity and signed-note tests. The Postgres race test did not run.
Limits & open issues
The attestation signature is an unkeyed SHA-256 of (attester, type, id, decision), not a cryptographic signature; integrity rests on the HMAC-anchored provenance chain and audit log. Signing a note does not cascade to its facts, which are attested one by one. A role intended mainly for administration (practice manager) also holds sign permissions in the solo-pilot role seed; this is a recorded open decision. The race-condition tests run only in the Postgres lane, which CI does not run.
7.9Chart commitment· System1 · Verified
What the user does
Nothing. The chart reflects the decisions straight away.
What the system does
There is no separate commit step: the chart is the set of current, non-retracted clinical_fact rows, and attestation changes their status in place. GET /api/patients/{id}/state (clinical_state_service) shows pending facts flagged. Closing the encounter writes a rollup timeline event. Provenance and outbox events are appended.
AI involvement
None.
Safeguards
Hash-chained provenance with a signed anchor. Postgres triggers are designed to block UPDATE and DELETE on the audit table (migration 0026); those trigger tests run only against Postgres and were not run (see §16).
Result
An updated chart, timeline and audit trail.
Test evidence
test_provenance_anchor.py, test_provenance_concurrency.py, test_encounter_rollup.py, test_governance_invariants*
Verification on a07bc2a
Run and passed: G01 fact versioning (19), G02 provenance (6), G18 chain verification (27, SQLite cases). 24 Postgres-only cases skipped.
Limits & open issues
The tie-break when ordering provenance is a recorded low-severity defect. Redelivery of events that missed a subscriber depends on the worker process, which has no systemd unit.
7.10Subsequent updates and outbound transmission· Physician · System3 · Partial
What the user does
The physician edits a fact (for example a dose change), retracts a wrong one, or adds an addendum to a signed note. If an EHR connection is configured, the signed note is sent to the EHR.
What the system does
PUT /api/facts/{id} → supersede_fact, an atomic conditional close of the old row plus a successor (pending), raising FactConflictError on a race. POST /api/facts/{id}/retract. POST /notes/{id}/addendum → note_addendum (the signed text is never changed) and re-transmission as version ~vN. Outbound: ehr_writeback_service.auto_post_on_sign or a manual post. A refusal chain checks master switch → go-live phase → connection active → write enabled → workflow → MLLP receipt evidence → patient linked. Then FHIR R4 DocumentReference, or HL7 v2.5.1 MDM T02/T08 over MLLP/MLLPS, with an outbound_post row, retry and backoff.
AI involvement
None.
Safeguards
Only signed artefacts are sent. Host allowlist and HTTPS required. Write-back master switch is off in pilot/production by default. Idempotency identifiers.
Result
A versioned chart. Optionally, a document in the external EHR.
Test evidence
test_wp14_fact_edit.py, test_pilot_ehr_transfer.py, pilot_qa/test_i_hl7_mdm.py (live-stack lane), test_pilot_ehr_c5_mllps_tls.py, test_pilot_ehr_c6_mllp_receipt.py, test_hl7_adt.py
Verification on a07bc2a
Partly run: G01 fact edit and retract (19 passed). EHR transport tests exist (loopback fakes) and were not run here. The live-stack HL7/FHIR lane was not run.
Limits & open issues
Tested only against loopback fakes; no real EHR endpoint is configured. Some HL7 fields are hard-coded (MSH-11 processing ID, PID-3 assigning authority, TXA-2). The default go-live phase is full. SMART authorisation-code flow is not implemented. Retract lacks the conditional concurrency guard that supersede has. The system of record is undecided.

9Runtime architecture

JamEMR runs as a modular monolith on a single host: one FastAPI backend process, a separate static-UI server that also proxies /api, PostgreSQL 16, Redis, and local AI services (LLM, speech-to-text, OCR, embeddings) bound to loopback. The deployment of record is systemd units plus hardening drop-ins (deploy/systemd, deploy/phase5…8) on an NVIDIA DGX-class host shared with other GPU workloads, reached over a private tailnet. docker-compose.yml exists but has drifted (see findings).

11Data layer

Clinical fact ledger

clinical_fact holds every datum, with validity_start/validity_end, supersedes_fact_id, retracted_at, author_type, confidence and attestation_status. The "current chart" is the non-retracted, non-superseded set (/api/patients/{id}/state).

Provenance chain

provenance_entry stores prev_hash/entry_hash (a SHA-256 chain). provenance_anchor stores the chain head, HMAC-signed with a provenance key. Every fact write, attestation and note change appends to it.

Audit log

access_audit is hash-chained, HMAC-signed and anchored. Database triggers are designed to block UPDATE and DELETE (migration 0026); this was not verified, because its tests need Postgres and run neither in CI nor in this review. It holds identifiers and codes only, never free text. Every successful patient-scoped read is logged.

Events & workflows

event_outbox, timeline_event and workflow_instance/workflow_step form a DB-backed event bus and state machine (auto, human and wait steps). Redelivery depends on the separate worker process.

Migrations

A linear Alembic chain from 0001_baseline to 0056_portal_session_cutoff_audit_reason (0038 is intentionally absent; 0039 points back to 0037). Notable revisions: 0003 encrypted demographics · 0006 provenance anchor · 0007 audit integrity · 0024/0025 care team and practice-scope grants · 0026 immutable audit · 0027 PHI lifecycle · 0034 recording consent · 0042 EHR connections · 0052 outbound claim · 0054 pilot field encryption · 0055 audio blobs. In pilot and production, schema is owned by Alembic only (no create_all). CI checks for model/migration drift, on SQLite only.

Encryption

  • Field level: EncryptedText (36 uses) and EncryptedJSON (12 uses) across 15 model files. AES-256-GCM, with per-field keys derived by HKDF from a KMS root. KMS backends: local (dev), environment root key, HashiCorp Vault Transit (code exists, not deployed). Reads tolerate legacy plaintext; rotation and sealed-column verification scripts exist.
  • Disk: LUKS volume with a mount guard. In pilot/production the backend refuses to start if blob, backup, temp or import paths are not on the encrypted mount.
  • Backups: age- or openssl-envelope-encrypted pg_dump, a restore-verification script and a freshness timer. A restore drill is recorded on synthetic data only.

Tenancy

Single practice. There is no tenant or practice identifier on clinical tables. Access is scoped per patient through care-team rows or explicit, expiring practice-scope grants, enforced by middleware. Running multiple practices would need a data-model change. The repository records it as an open architecture decision.

12AI stack

One governed entry point

backend/app/ai/runtime.py: complete() posts OpenAI-style chat completions to JAMEMR_LLM_BASE_URL. Each call writes an ai_event (model, prompt version, system-prompt hash, latency, server fingerprint, app build) and an audit entry, and alerts on a model change. A 120 s per-call timeout is backed by a hard wall-clock deadline. 21 modules call it. Two extraction services make their own HTTP calls but reuse its deadline and metadata helpers.

Governance

ai/governance.py refuses prohibited actions (prescribe, sign order, finalise diagnosis, submit claim, attest note). AI facts always land pending attestation. The assistant's actions need confirmation and have a capped autonomy level.

PHI fail-closed

PHI mode is forced on in pilot/production. All PHI HTTP goes through guarded_urlopen (strict loopback, no redirects, no proxies, one attempt). Only approved local models may be used. External terminology and drug-interaction APIs are blocked. Cloud models need an explicit flag plus a signed vendor BAA, and are never used on PHI.

Models & routing

model_router.py: first pass medgemma-27b, optional cleanup qwen2.5:32b (off), frontier model only for evaluation on de-identified data. Configured aliases include jamemr-local and jamemr-medical. Which model actually serves an alias depends on the host. The pinned manifest shows several aliases resolving to one 4.7 GB model.

13Security & compliance controls

Enforced in code: boot refuses unsafe configuration

  • Dev secrets (JWT, provenance key, field-encryption key) are refused in pilot/production, as is authentication turned off.
  • SQLite is refused in pilot/production. Redis is required in production.
  • In PHI mode, LLM, embedding and OCR endpoints must be loopback on approved ports. There is a data-region assertion.
  • A storage guard requires an encrypted mount for all PHI paths, and an environment-isolation check stops dev and prod from sharing a database, keys or storage.
  • Production refuses to run under a coding-assistant context, and refuses cloud models without signed BAAs.
  • In PHI mode, core dumps are disabled and the temp directory is pinned.

Request pipeline

web_hardening → request_id → portal_ip_gate → log_phi_access → enforce_pilot_auth → enforce_module_switches → enforce_patient_scope, followed by per-route role and permission checks with an audited break-glass path.

Authentication

Signed bearer tokens with jti, revocation and refresh. PBKDF2 passwords, login rate limiting, a 15-minute idle timeout and an absolute session cap. TOTP MFA (enforced only for configured roles; the default list is empty). OIDC authorisation code + PKCE that maps only to existing users; its pending-flow state is held in memory, which assumes a single worker.

Authorisation registries

Every /api route must be classified (no-PHI, patient-scoped, practice-scoped, service-only) in route_inventory.py, declared in permission_declarations.py, and mapped to an audit event in audit_policy.py. Tests fail on any unclassified route. Reference docs are generated from these registries.

Web hardening

A strict CSP with a per-response nonce. Inline styles and event handlers are removed and tests forbid their return. No CORS. CSRF protection for cookie flows. API docs disabled in production. HSTS when TLS hostname verification is configured. Validation errors never echo input.

Egress

An allowlist table of every outbound integration. Only the local model endpoint is allowed by default. Messaging, fax, terminology, cloud LLMs, the IdP, cloud document stores, EHR FHIR and off-host backup are all denied unless named in JAMEMR_EGRESS_ALLOW.

Configuration-dependent, and not established as in force

MFA role list, OIDC, retention periods (categories exist; no period is active), egress allowlist, TLS/HSTS, host firewall, backup schedule and off-host copy, monitoring. The repository's own readiness assessment (19 Oct 2026) lists open items in each of these areas for the pilot host. The repository records 0 of 15 HIPAA policies as adopted, no security risk analysis, no penetration test and no signed BAAs. These are organisational gaps, not code gaps, but they gate any real-patient use.

17Engineering findings

Each of these was confirmed by reading the code (file references given). They are the issues most relevant to an engineering partner. They are not a full defect list; the project tracks its own clinical-logic defects separately.

F1 · high  Deployment templates contradict the boot guards

.env.pilot.example and deploy/systemd/jamemr.env.example set JAMEMR_ENV=pilot with a SQLite URL, which assert_database_safe refuses. Both also point the LLM at port 4000, while PHI mode approves only 11434 by default (security/phi_egress.py). Only deploy/production.env.example is consistent with the code.

Direction: Reproducible, validated environment templates generated from one source.

F2 · high  Background worker is not deployed under systemd

Outbox redelivery and workflow retry/resume run in python -m backend.app.workers, which is defined only in docker-compose.yml. deploy/systemd/ has no worker unit, so in the systemd deployment those loops probably do not run (inferred from deployment files).

Direction: Add a supervised worker service with health checks and alerting.

F3 · high  CI does not test the production database or the release branch

CI runs SQLite only. Eighteen Postgres-gated test files (attestation races, audit triggers, concurrent boot, migrations on Postgres) never run in CI, although production is Postgres. Pushes to release/pilot-rc do not trigger CI. There is no lint, type check, coverage, SAST or dependency audit, and main is unprotected.

Direction: Postgres service container lane, release-branch triggers, security scanning, branch protection.

F4 · high  Single node, single worker, single GPU; in-process state

One uvicorn worker. OIDC pending flows and PI-consult jobs are held in process memory, and ASR and record review are serialised on one shared GPU. HA, PITR and failover exist only as a design document.

Direction: HA Postgres, externalised state (Redis), worker scaling, dedicated inference capacity.

F5 · high  Import commit swallows attestation failures

services/import_service.py (~L3405–3413) wraps the reviewer attestation in try/except: pass. A failed attestation leaves a fact silently unattested while the commit reports success.

Direction: Fail the item and surface it, or queue it for review.

F6 · medium  docker-compose and requirements have drifted

backend/requirements.txt, which the Dockerfile uses, omits alembic, cryptography, PyJWT, redis and requests, which pyproject.toml requires. The compose OCR port collides with another service. As written, the Docker path is unlikely to boot under the pilot posture.

Direction: One dependency source of truth and a container build in CI.

F7 · medium  AI provenance labels are inaccurate

LLM extraction facts are stamped with JAMEMR_LLM_MODEL although the call used the ambient model. Deterministic note renders are labelled with a model name. The pinned model manifest maps several aliases to one 4.7 GB digest. Model identity in audit data is less precise than it appears.

Direction: Record the server-reported model and digest per fact; align alias governance.

F8 · medium  Attestation "signature" is an unkeyed hash

attestation_service.py L222: sha256(attester|type|id|decision). Integrity actually comes from the HMAC-anchored provenance chain and audit log. The field name overstates it.

Direction: Rename it, or use a keyed/asymmetric signature (KMS-backed).

F9 · medium  Specialty coupling in the ambient path

Deterministic ambient extractors and the ambient note are neurology-only. The A–Y note generator embeds a hard-coded clinician signature constant (clinical_note_service.py L31).

Direction: Plugin interface per specialty; signature from the signer's profile.

F10 · medium  Interop defaults and hard-coded HL7 fields

connection_policy_service.DEFAULT_PHASE = "full". MDM messages hard-code MSH-11, PID-3 assigning authority and TXA-2. These are mitigated by the write-back master switch being off in production-like mode.

Direction: Safer default phase; configurable HL7 profile per partner; interface-engine conformance testing.

F11 · medium  Retract lacks the concurrency guard supersede has

fact_service.retract_fact has no conditional claim, unlike supersede_fact.

Direction: Conditional UPDATE with conflict error, as in supersede.

F12 · medium  Monolithic frontend file

frontend/workspace.html is about 6,300 lines (about 613 KB) of vanilla HTML and JS with no build step or module system. Tests guard the CSP rules, but the file is costly to change safely.

Direction: Incremental modularisation (ES modules / components) behind the existing browser tests.

F13 · medium  Single-practice data model

No tenant or practice identifier on clinical tables. Access scoping is per patient.

Direction: Tenancy ADR before any multi-practice commitment.

F14 · low  Stale top-level documentation

The README describes a Next.js frontend and "Phase 0". The command-centre document (July) describes an older topology.

Direction: Regenerate the overview docs from code, as is already done for the security registries.

F15 · low  Unused agent definitions

agents/ (LangGraph sketch, prompt markdown, tool registry) is not referenced at runtime. The live prompts are inline constants.

Direction: Move prompts to the existing prompt registry, or delete the dead material.

F16 · low  Retention not configured

Retention categories and a six-year floor exist, but no active periods are set and auto-delete is off.

Direction: Policy decision, then configuration and scheduled enforcement.

DGlossary

Attestation
A clinician's recorded approve or reject decision on a fact or note, bound to the exact reviewed text (for notes) and logged with provenance.
Pending attestation
The status of every AI- or device-authored fact until a human decides on it.
Provenance chain
An append-only, hash-linked log of every change to clinical data, with an HMAC-signed head anchor.
PHI mode
The posture in which all model and network calls are restricted to approved local endpoints. It is forced on in pilot and production.
Ambient visit
A consented recording of the visit conversation that is transcribed and turned into draft facts and a draft note.
Precheck
A server-side readiness check before signing. It returns blockers, warnings and the text hash that the sign request must echo back.
Supersede
Edit by succession: the old fact is closed, and a linked successor is created in pending attestation.
MDM / MLLP
HL7 v2 Medical Document Management messages, and the Minimal Lower Layer Protocol used to transport them.
Knowledge Foundry
An external pipeline that produces verified knowledge bundles, which JamEMR imports and checks by hash.
